§01
what we want · the vision

A teammate, not a tool.

Tools don't have continuity, don't hold opinions, don't get held accountable. Sym is more than that — a colleague that happens to be very fast at lookups, very patient with repetitive work, very literal about confidentiality.

The workspace is the substrate. Chat is where teams already are. Any AI that lives outside it asks the team to context-switch to it. Sym lives inside. Continuity is the killer feature. A teammate that remembers what was said last week — and what was decided in a channel they aren't currently in — has compounding value.

Trust is a system property, not a vibe. Scope discipline, provenance, auditability, reversibility. Where trust and capability conflict, trust wins. And the agent is the product — not the model. Swap providers and the team's experience is unchanged.

behaviour №0101

Gets added to channels and DMs by name. Other people @ them.

behaviour №0202

Picks up which channels are formal and which are casual without being told.

behaviour №0303

Remembers what they were told last Tuesday when it comes up Friday.

behaviour №0404

behaviour №0505

Takes on small, repeating work — "watch this PR," "post the deploy digest Mondays."

behaviour №0606

Has a paper trail. You can ask why they did something — they can show you.

the teammate test · cheapest correctness check

Would a thoughtful new hire do this? If no, Sym doesn't either.

01. Forward a message from #execs to #general? No
02. Take an irreversible action without asking? No
03. Make a guess and say "I think this is right"? Yes
04. Randomly speak up in #general at 3am? No
05. Say "I'm not sure, let me find out"? Yes
06. Confabulate when memory is empty? No
§02
what we build · v1 architecture

Dashboard-first. Two servers. Five memories. Receipts on everything.

The dashboard is the configuration source of truth. Sym (the Slack agent) reads everything it needs from Postgres — what providers to use, which MCPs are installed, who's allowed, what soul to wear. Two separate deployables, one shared store.

Two servers, one Sym. The Dashboard (Next.js + Tailwind + shadcn) is where admins configure providers, install MCPs and skills, edit soul layers, manage ACL and cross-user grants, view audit + activity. The Agent (Hono + custom thin loop) is the Slack-side runtime. Both deployables read and write to the same Postgres + Redis. Config-as-database means live-reload is free — dashboard writes, agent sees it on the next turn.

// dashboard Control plane The admin surface where everything is configured. Slack install flow lives here. Without the dashboard, Sym has nothing to do.
// agent Slack runtime The Hono server that ingests Slack events, runs the agent loop, and posts replies. Reads its config from Postgres on every turn.
// shared stores One source of truth Postgres holds config + memory + audit + transcript + OAuth. Redis holds locks + sessions + rate-limit + hot cache.
// audit Receipts on everything Every config change, every recall, every tool call, every reply. Hash-chained. Streamed live to the Dashboard's activity feed.

Memory · five scopes · indefinite retention scoped knowledge with a change policy
scope 01
Workspace
visible to · all members
Org-wide truths: glossary, ownership map, policies, "how we do things here."
scope 02
Channel
visible to · channel members
Channel norms, active topics, decisions made here. Cannot leak across channels.
scope 03
Thread
visible to · thread participants
Tight transient context for one thread. Narrow recall window by default.
scope 04
DM
visible to · the user only
Per-user preferences, name pronunciation, tone choices, private workflows.
scope 05 · new
Custom relational
visible to · grantor + subject
Facts User A told Sym about User B — keyed on (actor, subject) with explicit consent rules.

change policy

Retention is indefinite. The interesting question isn't "when do we forget?" — it's "when do we change what we know?"
add
New fact is independent of existing memories. Explicit "remember this," repeated mention, preference statement, or detected habit.
update
New fact refines an existing memory without contradicting it. Reinforce confidence, sharpen wording. Audit trail preserved.
supersede
New fact contradicts an old one. Old memory is marked superseded (kept for audit), new memory becomes authoritative.
ignore
Casual chitchat, jokes, one-off passing mentions, Sym's own output, failed tool calls. Never enters memory.
Soul · cascading personality how it sounds, layered · live-reload
L0 sym.soul.md Global voice · the teammate posture. Hedge appropriately. Confirm before destructive actions. Never confabulate.
L1 workspace.soul.md Workspace tone floor (casual · neutral · formal). Edited via Dashboard.
L2 channel/<name>.soul.md Per-channel override. #execs formal · #pets casual · admin-set or auto-suggested.
L3 user/<id>.soul.md Per-user preference. Set via DM ("Sym, talk to me less formally") or Dashboard.
Cascade rule: more-specific layers override less-specific. Final voice is a CSS-like merge, applied by the runtime as a tone-rewrite stage after the agent produces draft text. A substance-diff guard rejects rewrites that change facts. Soul files live in Postgres, edited via Dashboard, picked up live by the next turn.

Trust · the boundary credentials, access, isolation
isolation
Sandbox + egress proxy
Tools run in per-turn Docker + gVisor sandbox. Outbound traffic routes through an egress proxy that injects short-lived, requester-bound credential leases. Secrets never reach the model OR the sandbox filesystem.
credentials
Per-user + dashboard grants
Each user OAuths their own providers. Cross-user grants are issued via the Dashboard with a Slack text confirmation back to the grantee. Time-boxed, scope-restricted, revocable. Every cross-user call audited with actor + on_behalf_of.
access
ACL on Slack + Dashboard
Allowed/restricted users gate Slack interaction and Dashboard access separately. Secrets in Postgres are encrypted at rest. The Dashboard install flow is the only way to bootstrap a new admin.
§03
how we build · structure, stack, sequence

Dashboard-first. Config-as-database.

One canonical implementation per concern. The Dashboard ships first; everything else reads its truth from Postgres. Lower-level primitives composed upward.

Principle: the Dashboard is the source of truth. Sym (the Slack agent) is a stateless config-consumer that reads what to do from Postgres on every turn. No file-based config in v1. Config changes are live; the next turn sees the new world.
