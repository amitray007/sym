§01
what we want · the vision

A teammate, not a tool.

Tools don't have continuity, don't hold opinions, don't get held accountable. Sym is more than that — a colleague that happens to be very fast at lookups, very patient with repetitive work, very literal about confidentiality.

The workspace is the substrate. Chat is where teams already are. Any AI that lives outside it asks the team to context-switch to it. Sym lives inside. Continuity is the killer feature. A teammate that remembers what was said last week — and what was decided in a channel they aren't currently in — has compounding value.

Trust is a system property, not a vibe. Scope discipline, provenance, auditability, reversibility, compliance. Where trust and capability conflict, trust wins. And the agent is the product — not the model. Swap providers and the team's experience is unchanged.

behaviour №0101

Gets added to channels and DMs by name. Other people @ them.

behaviour №0202

Picks up which channels are formal and which are casual without being told.

behaviour №0303

Remembers what they were told last Tuesday when it comes up Friday.

behaviour №0404

Doesn't repeat confidential information from one channel to people without access.

behaviour №0505

Takes on small, repeating work — "watch this PR," "post the deploy digest Mondays."

behaviour №0606

Has a paper trail. You can ask why they did something — they can show you.

the teammate test · cheapest correctness check

Would a thoughtful new hire do this? If no, Sym doesn't either.

01. Forward a message from #execs to #general? No
02. Take an irreversible action without asking? No
03. Make a guess and say "I think this is right"? Yes
04. Randomly speak up in #general at 3am? No
05. Say "I'm not sure, let me find out"? Yes
06. Confabulate when memory is empty? No
§02
what we build · v1, the actual MVP

Slack-first. One workspace. Five memories. Receipts on everything.

A small set of opinionated, owned defaults. Slack-deep, not Slack-abstract. MCP-first for extensions but with CLI fallback when needed. Receipts on every reply, audit on everything.

One Sym = one workspace. Slack only, but deeply Slack-native — Block Kit, modals, App Home, slash commands, message shortcuts, reactions, canvases. Extensions are MCP servers first (declarative config, no code) with a CLI-fallback path when a provider has no MCP yet. Memory lives in five scopes with a formation policy that decides what's substantial enough to remember. Tone is a cascading set of soul files. Credentials are per-user OAuth with optional cross-user grants. Access to Sym (Slack + the Sym Dashboard) is gated by an explicit ACL.

// adapter Slack-native, deep Block Kit, modals, slash commands, message shortcuts, App Home, reactions, canvases. We lean into Slack — no abstraction tax.
// runtime + sandbox Loop & trust boundary Our own thin agent loop on Fireworks. Tools run in a per-turn Docker+gVisor sandbox. Egress proxy injects short-lived, requester-bound credentials.
// memory · soul What it knows, how it sounds Five memory scopes with formation policy. Cascading soul files for voice. Strictly separated stores.
// audit · otel Receipts on everything Hash-chained audit log. OTel semantic keys. Live feed to the Sym Dashboard. Every reply carries a structured receipt.

Memory · five scopes + formation policy what it remembers, why, when
scope 01
Workspace
visible to · all members
Org-wide truths: glossary, ownership map, policies, "how we do things here."
scope 02
Channel
visible to · channel members
Channel norms, active topics, decisions made here. Cannot leak across channels.
scope 03
Thread
visible to · thread participants
Tight, transient context for one thread — narrow window, fast eviction.
scope 04
DM
visible to · the user only
Per-user preferences, name pronunciation, tone choices, private workflows.
scope 05 · new
Custom relational
visible to · grantor + subject
Facts User A told Sym about User B — keyed on (actor, subject) with explicit consent rules.

formation policy

Only write memory when the behaviour is substantial. Casual chitchat doesn't become memory.
Explicit "remember this" / "from now on"Yes
Repeated mention (≥2× across turns)Yes
Preference statement: "I prefer X / always X / never X"Yes
Tool-call habit (same flow run 3+ times)Yes
One-off fact mentioned in passingNo
Casual chitchat · jokes · banterNo
Sym's own output (no self-reference)Never
Failed tool calls or errorsNo
Soul · cascading personality how it sounds, layered
L0 sym.soul.md Global voice · the teammate posture. Hedge appropriately. Confirm before destructive actions. Never confabulate.
L1 workspace.soul.md Workspace-specific tone floor (casual · neutral · formal). Set at install, admin-tunable.
L2 channel/<name>.soul.md Per-channel override. #execs is formal · #pets is casual · admin or auto-suggested at install.
L3 user/<id>.soul.md Per-user preference. Set via DM ("Sym, talk to me less formally"). Stored in DM-scope memory.
Cascade rule: more-specific layers override less-specific. Final voice is a CSS-like merge, applied by the runtime as a tone-rewrite stage after the agent produces draft text. A substance-diff guard rejects rewrites that change facts.

Trust · the boundary credentials, access, isolation
isolation
Sandbox + egress proxy
Tools run inside a per-turn Docker + gVisor sandbox. Outbound traffic routes through an egress proxy that injects short-lived, requester-bound credential leases. Secrets never reach the model OR the sandbox filesystem.
credentials
Per-user MCP + grants
Each user OAuths their own provider accounts. Cross-user access only via explicit, time-boxed, scope-restricted grants from the credential owner. Every cross-user call audited with actor + on_behalf_of.
access
ACL on Sym itself
Allowed/restricted users gate the Slack interface and the Dashboard separately. Default modes: open, allowlist, or workspace_minus_blocked. Dashboard access usually narrower than Slack access.
§03
how we build · structure, stack, sequence

Owned defaults. Composable primitives.

One canonical implementation per concern. Abstractions arrive with their second use, not before. Lower-level primitives first; higher-level orchestration composes them.

Principle: always start at the lowest practical layer and compose upward. If a higher layer needs to swap an implementation, lift the interface at that moment — not preemptively.
